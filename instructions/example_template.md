# Writing mathematical notes

## Adding a page

1. Create a `.md` file under `src/content/docs/` with title frontmatter:

   ```markdown
   ---
   title: Descriptive page title
   ---

   ## First section

   Notes go here.
   ```

   Starlight renders the title; do not add a second H1. No imports or HTML anchors are needed. Use `.mdx` only for imported components.
2. To include the page in the sidebar, add a `slug` entry to the appropriate group in `src/data/navigation.json`: its path relative to `src/content/docs/`, without `.md` or a leading slash, e.g. `mathematics/problems/new_problem`. An optional `label` overrides the title. Preserve the curated groups and order.
3. Preview the page, check its math/navigation, and follow the [workflow](../README.md#workflow).

The sidebar controls presentation, not page creation. Notes without entries still get URLs, search indexing and sitemap entries unless explicitly excluded. No theorem inventory or snapshots need updating. `public/llms.txt` is an optional curated guide, not a page inventory.

If manual sidebar entries become burdensome, use Starlight's native [autogenerated groups](https://starlight.astro.build/guides/sidebar/) rather than a custom generator; preserve existing editorial navigation deliberately.

## Links and IDs

Filenames determine URLs, preserving case and underscores. Use ordinary Markdown links, including source-relative links (`[a result](../other-note.md#thm-result)`), same-page fragments (`[definition](#def-limit)`), and reference-style links. Root-relative site paths and external URLs also work.

Headings receive IDs automatically from source text/LaTeX, with `_1`, `_2`, … for repeats; the page title is `#_top`. Prefer explicit semantic-block IDs for referenced results. Explicit block IDs begin with a letter and contain letters, digits, `_`, `.` or `-`; they are case-sensitive and need only be unique within a page.

When renaming pages/IDs, update internal links and any proof metadata. Do not add invisible aliases just to preserve old external links.

Static images can use Markdown or HTML when attributes are needed, e.g. `<img src="/assets/triangle.png" alt="Projection geometry" width="50%">`.

## Mathematics

Use `$f(x)=x^2$` inline and `$$` on separate lines for display math:

```markdown
$$
\begin{align*}
f(x) &= x^2 + 2x + 1 \\
     &= (x+1)^2.
\end{align*}
$$
```

KaTeX renders at build time; invalid math fails the build. Use `$...$`/`$$`, not `\(...\)`/`\[...\]`. Break long chains with `align*` and `\\`; wide math scrolls within its container.

## Semantic mathematical blocks

Use directive containers; no imports or JSX are needed:

```markdown
:::definition[Limit point]{#def-limit-point}
A *limit point* of $F \subseteq \mathbb{R}$ is a point $x$ such that …
:::

:::theorem[A useful result]{#thm-result}
The statement, with ordinary Markdown and $\LaTeX$.
:::

:::proof
The proof goes here. $\blacksquare$
:::
```

Kinds: `definition`, `theorem`, `lemma`, `proposition`, `corollary`, `example`, `proof`, `remark`, and `notation`. Titles support inline math/Markdown and may be omitted; the kind is included in the rendered label. IDs are optional unless the block is referenced or carries proof relationships.

Use `remark` for mathematical observations and `notation` for symbol/convention setup:

```markdown
:::remark[About the hypothesis]{#rem-hypothesis}
The assumption is used only in the final step.
:::

:::notation{#not-space}
Write $X$ for the underlying space.
:::
```

Native Starlight `note`, `tip`, `caution`, and `danger` remain available for general annotations and warnings. Exercises and solutions can remain ordinary headings.

Proofs use native `<details>`, initially closed. Add `{open}` to start expanded, e.g. `:::proof{open}`. Do not use `open="false"`: HTML boolean attributes are true when present.

For nesting, use a longer outer fence:

```markdown
::::theorem[Result with a nested proof]{#thm-nested}
Statement.

:::proof
Proof content.
:::
::::
```

Links to identified mathematical blocks get hover/keyboard-focus previews automatically. Hash navigation opens containing proofs with JavaScript; ordinary links and proof disclosure remain usable without it.

### Optional proof relationships

**Not required for ordinary writing.** Add these only when deliberately recording what a proof establishes or uses:

```markdown
:::proof[Proof]{#proof-result proves="#thm-result" uses="#def-limit-point ../other-note.md#lem-helper"}
The proof goes here.
:::
```

- `proves` names exactly one result. `uses` is a whitespace-separated list and requires `proves`. References use the same syntax as links; relationship-bearing proofs need explicit IDs.
- Targets must be identified `definition`, `theorem`, `lemma`, `proposition`, `corollary`, or `example` blocks. Remarks, notation, asides and proofs can be linked normally, but are not relationship targets.
- Ordinary links imply no dependencies. Do not infer relationships from prose or annotate existing proofs without the author's intent.

Identified blocks automatically appear in `/theorems.json` with Markdown statements, source locations, URLs and declared relationships; nested proofs are excluded from result statements. There is no graph UI or manually maintained graph data. Unknown block types/options, duplicate block IDs and invalid declared relationships fail validation.

## Exercise notes and transcription

Preserve the author's mathematics and wording unless corrections are requested. Establish source abbreviations once, e.g. Axler's *Measure, Integration & Real Analysis* (MIRA), then use `(MIRA, 2.5)` consistently.

A useful structure is `## Exercise 1`, `### Question`, `### Solution`, with optional **Key idea:**, **(i)** / **(ii)**, italic first-use terms, and `$\blacksquare$` at the end of proofs. This is a convention, not required boilerplate.
