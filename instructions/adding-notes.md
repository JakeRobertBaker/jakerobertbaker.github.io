# Adding and maintaining notes

For Markdown syntax, page structure and transcription conventions, use [Notes Transcriber — Markdown conventions](example_template.md). That file is self-contained so it can also be uploaded to a ChatGPT project. Keep the syntax rules there; this guide covers repository integration and optional advanced metadata.

## Adding a page

1. Create a `.md` file under `src/content/docs/`, following the template's frontmatter and formatting conventions. Use `.mdx` only when imported components are needed; React is not installed or required.
2. To include the page in the sidebar, add a `- slug:` entry to the appropriate group in `src/data/navigation.yaml`: its path relative to `src/content/docs/`, without `.md` or a leading slash, e.g. `mathematics/problems/new_problem`. An optional `label` overrides the title. Preserve the curated groups and order.
3. Preview the page, check its math/navigation, and follow the [workflow](../README.md#workflow) and [preview instructions](site-preview.md).

The sidebar controls presentation, not page creation. Notes without entries still get URLs, search indexing and sitemap entries unless explicitly excluded. No theorem inventory or snapshots need updating. `public/llms.txt` is an optional curated guide, not a page inventory.

If manual sidebar entries become burdensome, use Starlight's native [autogenerated groups](https://starlight.astro.build/guides/sidebar/) rather than a custom generator; preserve existing editorial navigation deliberately.

## URLs and rendering

Filenames determine URLs, preserving case and underscores. When renaming pages/IDs, update internal links and any proof metadata. Do not add invisible aliases just to preserve old external links.

Heading IDs derive from source text/LaTeX, with `_1`, `_2`, … for repeats. KaTeX renders at build time; invalid math fails the build. Wide math scrolls within its container.

Proofs use native `<details>`. Hash navigation opens containing proofs with JavaScript; ordinary links and proof disclosure remain usable without it.

## Optional proof relationships

**Not required for ordinary writing or transcription.** Add these only when deliberately recording what a proof establishes or uses:

```markdown
:::proof[Proof]{#proof-result proves="#thm-result" uses="#def-limit-point ../other-note.md#lem-helper"}
The proof goes here.
:::
```

- `proves` names exactly one result. `uses` is a whitespace-separated list and requires `proves`. References use the same syntax as links; relationship-bearing proofs need explicit IDs.
- Targets must be identified `definition`, `theorem`, `lemma`, `proposition`, `corollary`, or `example` blocks. Remarks, notation, asides and proofs can be linked normally, but are not relationship targets.
- Ordinary links imply no dependencies. Do not infer relationships from prose or annotate existing proofs without the author's intent.

Identified blocks automatically appear in `/theorems.json` with Markdown statements, source locations, URLs and declared relationships; nested proofs are excluded from result statements. There is no graph UI or manually maintained graph data. Unknown block types/options, duplicate block IDs and invalid declared relationships fail validation.
